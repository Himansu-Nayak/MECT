## 1. EXISTING RECEIPT ARCHITECTURE FINDINGS

A forensic audit of MECT's financial persistence layer was conducted across the backend codebase (`DonationLifecycleService.java`, `DonationReceipt.java`, `ReceiptPdfService.java`, `PortalAccountController.java`, and `AdminDonorController.java`).

### Architectural Topology
1. **Receipt Entity Persistence:** Receipts are stored in the relational table `donation_receipts`, governed by Flyway migrations `V8__donations_payments_and_receipts_schema.sql` and `V11__donation_ecosystem_cms_and_rbac.sql`.
2. **Schema Fields:**
   - `id`: Bigint primary key.
   - `donation_id`: Unique foreign key to `donations.id` (enforcing strict 1:1 donation-to-receipt relationship).
   - `receipt_number`: Serialized institutional identifier (`MECT-RCPT-YYYY-XXXXXXXX`).
   - `donor_display_name`: Either the donor's legal full name or `"Anonymous Donor"`.
   - `programme_name`: Name of the designated charitable programme.
   - `amount`: Exact decimal monetary contribution.
   - `currency`: ISO code (`INR`).
   - `receipt_type`: `"INSTITUTIONAL_PAYMENT_RECEIPT"`.
   - `statutory_note`: Text generated by `PaymentConfigurationService.getStatutoryReceiptNote()`.
   - `pdf_bytes`: In-memory generated OpenPDF document bytes stored directly as binary in PostgreSQL.
   - `pdf_sha256`: SHA-256 hex digest of `pdf_bytes` for cryptographic anti-tamper verification.
   - `created_at`: Immutable UTC audit timestamp.

## 2. ACTUAL `ReceiptPdfService` CALL-SITE AUDIT

The `ReceiptPdfService` generates A4 PDF documents in memory using OpenPDF (`com.lowagie.text.*`).

### Call-Site Audit Results
- **Call-Site 1 — `DonationLifecycleService.java` (Line 40870):**
  Triggered when an incoming payment transitions to `SUCCESS`. This occurs either synchronously via Cashfree order verification (`verifyCashfreePayment`), asynchronously via Razorpay/Cashfree webhook handlers, or upon manual administrator approval of a bank transfer claim.
- **Call-Site 2 — Dynamic Dynamic QR Service (`HimPaymentService.java`):**
  Invoked when an authenticated dynamic UPI settlement is acknowledged.
- **Strict Invocation Guard:**
  `receiptPdfService.generateReceiptPdf(...)` is wrapped in:
  ```java
  DonationReceipt receipt = receiptRepository.findByDonationId(donation.getId()).orElseGet(() -> {
      ...
  });
  ```
  This guarantees that once a receipt is persisted for a donation, subsequent calls return the existing record without regenerating or re-hashing.

## 4. SHA-256 STORAGE AND VERIFICATION DETAILS

To verify that receipts are genuine and tamper-evident:
1. **Generation:** When `ReceiptPdfService` finishes writing `baos.toByteArray()`, `DonationLifecycleService` computes `HmacCryptoUtil.sha256Hex(pdfBytes)`.
2. **Storage:** Stored in `donation_receipts.pdf_sha256` as a 64-character lowercase hexadecimal string.
3. **Verification Test:**
   - Test `testSuccessfulPaymentGeneratesPersistedReceiptWithSha256` proved that re-hashing the stored PDF bytes produces the exact stored hash.
   - Test `testHashVerificationDetectsAlteredPdfContent` proved that altering even a single byte (`tampered[len - 1] ^ 0xFF`) results in a mismatch (`tamperedSha256 != storedSha256`).
4. **Legal Distinction:** Hashing provides cryptographic file integrity; it is clearly documented as an internal integrity mechanism, **not** as a government digital signature or tax certificate.

## 6. SBI UTR VERIFICATION WORKFLOW

The manual State Bank of India transfer mechanism was forensically audited to confirm the core rule:
**A donor's UTR submission is a payment claim, not proof of settled funds.**

```sequence
Donor -> Frontend (/donate): 1. Transfer via SBI UPI QR or NEFT/IMPS
Donor -> Frontend (/donate): 2. Submit UTR (e.g. SBIN412345678901)
Frontend -> Backend: 3. POST /public/donations/sbi/submit-utr
Backend -> Database: 4. Persist Claim (status = UTR_SUBMITTED)
Backend -> Frontend: 5. Return "Bank Transfer Verification Pending"
[Zero receipts generated at this stage]
MECT Accounts -> Bank: 6. Inspect official SBI Corporate Statement
MECT Accounts -> Admin Portal: 7. POST /admin/manual-claims/{claimRef}/review (decision = VERIFIED)
Backend -> Database: 8. Update Claim (status = VERIFIED), Payment (status = SUCCESS)
Backend -> ReceiptService: 9. Generate Official Receipt PDF & Persist SHA-256
Backend -> Outbox: 10. Enqueue Receipt Email to Donor
```

### Forensic Checks
1. **Pending Status UI:** In `UnifiedDonationExperience.tsx`, submission displays:
   `Bank Transfer Verification Pending`
   With note:
   *"UTR submission is a payment claim, not proof of settled funds. An official receipt will be generated only after verified credit in MECT's bank statement."*
2. **Receipt Inaccessibility:** Verified via test `testManualSbiUtrIsClaimOnlyAndRequiresAdminVerification` that before administrative approval, zero receipts exist in the database.
3. **Duplicate Rejection:** Test `testDuplicateUtrSubmissionIsRejected` confirmed that submitting the same normalized UTR returns `HTTP 409 Conflict`.
4. **Audit Trail:** Approved claim reviews log `action='MANUAL_SBI_CLAIM_VERIFIED' resource='MANUAL_BANK_TRANSFER_CLAIM:<ref>' ip='...'`.

## 7. DONATION LIFECYCLE RECONCILIATION

The state lifecycle across `donations` and `payments` maintains atomic consistency:
- **`INITIATED`:** Temporary record created during pre-flight.
- **`PENDING`:** Active order awaiting donor instrument completion.
- **`SUCCESS`:** Funds confirmed by gateway cryptographic signature or manual bank verification. Receipt generated. Role upgrade to `ROLE_DONOR` granted to portal user.
- **`FAILED`:** Explicit gateway rejection. Order closed.
- **`EXPIRED`:** Stale pending transaction past 30-minute gateway window.
- **`REFUNDED`:** Reversal executed with full audit trail.

## 8. RECEIPT DUPLICATE-PREVENTION RESULTS

Duplicate prevention operates across three defense layers:
1. **Database Constraint:** `donation_receipts.donation_id` has a unique index (`UNIQUE KEY unique_donation_receipt (donation_id)`). Any attempt to insert a second receipt for the same donation throws a database integrity violation.
2. **Service Layer Guard:** `DonationLifecycleService` checks `receiptRepository.findByDonationId(donation.getId())` before generating PDF bytes.
3. **Webhook Deduplication:** Webhook events are logged in `payment_events` with unique `event_id`. Replays return immediately without processing.

Verified via test `testDuplicateWebhookDoesNotGenerateDuplicateReceipts`:
- First delivery: Created receipt `MECT-RCPT-2026-XXXX`.
- Second delivery: Returned `HTTP 200 OK`; database receipt count remained exactly 1.

## 9. REFUND AND CORRECTION BEHAVIOR

- **Audit Preservation:** Under no circumstances is an issued receipt record deleted upon refund.
- **State Transition:** The `payments.status` transitions to `REFUNDED`.
- **Reconciliation Record:** A corresponding entry is logged in `payment_reconciliation_logs` documenting the reason, reversal transaction reference, and approving administrator.
- **Receipt Note:** In the donor portal and admin ledger, the receipt status reflects that the underlying transaction has been refunded, preventing fraudulent secondary deduction claims.

     `PAN (Optional — for statutory reporting under Income-tax Act)`

   - Never exposed in URLs or query strings (POST body transmission only).

## 14. EMAIL DELIVERY-STATE VERIFICATION

The notification system uses an asynchronous transactional outbox (`NotificationOutboxService.java`):

1. **State Machine in `notification_outbox`:**
   - `PENDING`: Enqueued upon receipt generation.
   - `SENT`: Dispatched by configured provider (Resend / SMTP) with external message ID.
   - `RETRY_SCHEDULED`: Provider transient error; exponential backoff scheduled.
   - `FAILED`: Exhausted maximum retry count (5 attempts).
2. **Truthful Reporting:** MECT does not claim an email is "delivered" upon generation; it is logged as queued until the provider acknowledges dispatch.
